Week 1 · 执行模型

一个 kernel 怎样启动并落到 GPU 硬件？

从一次启动出发，连接线程组织、硬件执行、数据移动与结果检查，建立写第一个 MUSA 程序所需的完整路径。

本周要回答的问题

  • grid、block、warp、thread 分别描述什么？它们怎样映射到 MP？
  • 怎样让每个线程找到自己的数据，同时避免最后一个 block 越界？
  • CPU 和 GPU 之间怎样传递数据，又怎样确认 kernel 已完成且没有出错？

核心知识

1. 软件组织：一次启动到一个线程

kernel → grid → block → warp → thread：kernel 是设备函数，一次启动产生一个 grid；grid 包含多个 block，每个 block 包含线程，线程被组织成 warp 执行。这是并行工作的组织方式。

2. 硬件组织：GPU 到 MP

GPU → MPC → MPX → MP 描述 MUSA 硬件层级，具体数量和资源范围随架构变化。CUDA SM 可帮助理解 MP 的编程角色，但两家物理结构不能逐层画等号。详见 GPU 层级专题。

3. block 驻留，warp 执行

一个完整 block 驻留在一个 MP 上，不会拆到多个 MP。block 是资源分配与线程协作的边界，warp 是 SIMT 执行分组。warp 宽度与驻留资源上限要查询目标设备，不能照抄其他架构的常数。

4. 四个内置索引变量

threadIdx 是 block 内线程编号，blockIdx 是 grid 内 block 编号；blockDim 和 gridDim 分别是 block 和 grid 的维度。一维全局索引是 blockIdx.x * blockDim.x + threadIdx.x。

5. Host / Device 内存边界

本周使用普通 host 内存与 musaMalloc 分配的 device 内存：host 不能直接解引用 device 指针，kernel 也不能把普通 host 指针当作显存使用。用 musaMemcpy 显式传输数据，按 元素数 × sizeof(元素类型) 计算字节数，使用完后释放内存。

6. 启动成功不代表执行成功

musaGetLastError() 常用于检查 launch 配置错误；非法地址等异步执行错误要在同步点检查。普通 Runtime API 的返回值也应检查，避免把早先的问题误判成后续调用的故障。

7. launch 异步，同步确认完成

kernel 启动返回时，GPU 可能仍在执行。musaDeviceSynchronize() 成功返回可确认当前设备此前提交的工作完成。读取 host 结果还需要把数据拷回；本周默认流中的同步 D2H 拷贝会等待相关工作和拷贝完成。

关键代码

从线程位置得到数组位置

block 数通常向上取整，因此总线程数可能大于元素数。索引计算和边界保护要一起出现。下面将索引示例改写为数组写入，便于观察每个线程负责的位置。

全局索引与边界保护
int idx = blockIdx.x * blockDim.x + threadIdx.x;
if (idx < n) {
    output[idx] = idx;
}

分配、传入、计算、传回

这是带输入数据的流程示意：h_data 是已准备好的 host 缓冲区，d_data 是 device 指针，bytes 是数据字节数。原始示例在 GPU 上直接填常数，不需要 H2D 输入；这里补上 H2D 以展示完整方向。实际程序还要检查每个 API 返回值，并用 musaFree 释放显存。

Host / Device 数据流
musaMalloc(&d_data, bytes);
musaMemcpy(d_data, h_data, bytes, musaMemcpyHostToDevice);
kernel<<<grid, block>>>(d_data, n);
musaMemcpy(h_data, d_data, bytes, musaMemcpyDeviceToHost);

调试期的两步检查

先检查启动状态，再等待执行并检查异步错误。MUSA_CHECK 是本仓库自定义的辅助宏，不是 MUSA Runtime API，定义见 code/include/musa_common.h：出错时打印文件、行号和错误信息并退出。使用下方片段前，需将 code/include 加入编译器头文件搜索路径并引入 #include "musa_common.h"。Week 1 源码为连续演示多个错误，实际使用的是文件内定义、只打印不退出的 CHECK_SOFT。逐次同步便于定位问题，但会影响并发，后续应按实际依赖选择同步范围。

检查 launch 与异步执行
kernel<<<grid, block>>>(d_data, n);
MUSA_CHECK(musaGetLastError());
MUSA_CHECK(musaDeviceSynchronize());
查看源码：05_error_check.mu

注意事项

  • 遗漏边界保护：向上取整会产生多余线程，访问数组前先判断 idx < n。
  • 在 host 解引用 device 指针：同步不会把显存变成 host 数组，应先 D2H 拷贝再读取 host 缓冲区。
  • 把 musaMemset 当成按元素赋值：它按字节填充；填入 1 不等于把每个 float 设为 1.0f，应使用初始化 kernel 或 host 赋值后拷贝。
  • 相信 GPU printf 的输出顺序：线程与 block 的执行先后不固定，打印行的顺序不能证明索引或调度顺序。
  • 只检查 launch 错误：musaGetLastError() 成功不保证 kernel 没有越界；调试时还要检查同步返回值。

精选题目

先独立回答，再展开核对。题干、答案与易错点保留完整自测原文；其中 SM 使用 CUDA 类比语境，MUSA 对应的 block 驻留位置称为 MP，具体物理实现不能画等号。

kernel<<<grid, block>>> 里的 grid 和 block 分别控制什么？

答案：grid 决定启动多少个 block，block 决定每个 block 里有多少个 thread。

易错点：<<<2, 4>>> 是 2 个 block、每个 block 4 个线程，总共 8 个线程。

为什么常见 kernel 都要写 if (idx < N)？

答案：blocks = (N + threads - 1) / threads 保证线程数不少于 N，但不保证刚好等于 N。

易错点：多出来的线程必须主动退出，否则可能越界读写。

musaGetLastError() 和 musaDeviceSynchronize() 分别主要抓什么错误？

答案：musaGetLastError() 常用于抓 launch 配置错误；musaDeviceSynchronize() 等待 kernel 完成，并暴露异步执行中的错误。

易错点：调试期推荐 launch 后做两步检查，避免漏掉运行期 illegal address 等异步错误。

一个 block 会不会跨多个 SM 执行？

答案：一个 block 会被调度到同一个 SM 上执行。

易错点：block 内可以用 shared memory 和 __syncthreads() 协作，不同 block 不能直接这样同步。
