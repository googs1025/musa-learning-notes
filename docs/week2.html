本周要回答的问题

  • pageable 与 pinned host memory 的数据传输路径有什么差别？
  • 怎样区分 CPU 入队耗时、GPU kernel 时间和整条流水线的耗时？
  • 哪些 chunk 可以独立推进，哪些跨 stream 的读写必须等待 event？
  • Graph 何时值得重放，callback 又能告诉 host 哪些完成信息？

核心知识

1. Pageable 与 pinned

普通 malloc 取得 pageable host memory。传输时驱动通常需要内部 pinned staging 区中转；musaMallocHost 或 musaHostAlloc 分配的 page-locked 内存更适合 DMA。它优化的是 H2D/D2H 路径，分配和占住物理页也有成本，应控制大小并复用。

2. CPU wall-clock 要等工作完成

只用 CPU 时钟包住 kernel launch，主要得到入队开销。把完成同步包含在计时区间，才能覆盖 GPU 工作；这个数字也包含 host 提交、等待与同步成本。多流流水线的端到端时间要等所有相关 stream 完成后再结束计时。

3. GPU event 标记时间线

在同一 stream 按 start event → kernel → stop event 入队，等 stop 完成后读取 elapsed，可测量这段 GPU 时间。event 放在 H2D 之前就会把传输也算进去；不同 stream 上没有依赖的两枚 event 不能直接当作有序区间。先 warm-up，再做多次统计。

4. Unified memory 与 prefetch

musaMallocManaged 简化 host/device 指针使用，但数据驻留与迁移仍有成本。统一内存和 musaMemPrefetchAsync 的能力、迁移行为取决于平台、设备与 SDK；先检查支持情况和 API 返回值。本仓库示例会在 prefetch 不支持时跳过，每次 run 又会重新分配，第二轮不能直接称为同一批页的热启动。

继续阅读 统一内存与 prefetch 示例，核对目标平台的行为。

Stream、Event 与 Graph

同流 FIFO，跨流需要明确依赖

同一 stream 内的操作按提交顺序推进。不同 stream 没有天然的完成顺序；独立任务在资源允许时可以重叠。默认流的隐式同步还取决于 legacy、non-blocking 或 per-thread 等实际配置，不能仅凭流数量判断并发。

把 H2D → kernel → D2H 切成 chunk

多流示例把输入切成四份：每个 chunk 的 off=c*n 指向独立范围，同一条 stream 依次搬入 A/B、运行 vector_add、搬回 C。其他 stream 可推进其他 chunk，形成搬运与计算流水线。pinned buffer、异步拷贝和合适的 stream 配置提供重叠条件，最终收益仍受 copy engine、kernel 资源占用与 chunk 粒度限制。

每个 chunk 内：H2D(A/B) → kernel → D2H(C)。不同 chunk 使用不重叠的数组范围；host 等所有相关 stream 完成后，才读取结果或复用 buffer。

Event 连接生产者与消费者

fill_A 在 s1 写入数据后记录 a_done；s2 先等待该 event，再运行 square_to_b。musaStreamWaitEvent 为后续消费者操作建立设备端等待，host 可以继续提交其他任务。它只约束需要等待的工作，无需在这条依赖边上同步整个设备。

Capture → Instantiate → Replay

Graph capture 记录操作及其依赖，录制期间的 kernel 不实际计算。结束 capture 得到 graph，instantiate 得到可执行的 exec，之后每次 musaGraphLaunch 重放固定结构。示例将五个 add_one 录成一张图，观察重复提交的成本。

Graph 自身也有启动和构建成本。仓库记录的 AutoDL MTT、MUSA 3.1.0、每图五个小 kernel 实验中，Graph 曾慢于 direct launch；这只描述那组环境与工作负载。比较时应保持数据规模、操作数量和计时口径一致，说明是否包含构建成本，并记录设备、驱动、SDK 与重复测量结果。

Callback 是 host 完成通知

callback 示例在各 stream 的 kernel 后加入 on_chunk_done。运行时到达相应位置后执行 host 回调；跨 stream 的回调顺序可能不同于 chunk 提交顺序。回调中可投递 chunk_id 与状态，让主线程或 worker 处理后续工作。

按该示例及学习笔记记录的约束，callback 内不要调用 MUSA API 或再次 launch；保持通知轻量，避免重 CPU 工作或异常穿过 C 回调边界，具体限制以使用的 SDK 文档为准。示例的 counter=4 仅证明四次通知发生；判断成功还要检查 callback 的 status。

Pinned buffer 支撑异步传输

依据示例注释，把同步 benchmark 改写成异步 H2D 片段，沿用 h_pinned 与 d_dst；假定 device buffer、stream 和输入均已准备好。原 benchmark 实际使用 musaMallocHost 加同步 musaMemcpy，没有直接测量多流重叠。

02 · Pinned host memory 与异步 H2D（改写）
float* h_pinned = nullptr;
MUSA_CHECK(musaHostAlloc(&h_pinned, bytes, 0));
// 在 host 填充 h_pinned 后，提交传输。
MUSA_CHECK(musaMemcpyAsync(d_dst, h_pinned, bytes,
                          musaMemcpyHostToDevice, stream));
MUSA_CHECK(musaStreamSynchronize(stream));
MUSA_CHECK(musaFreeHost(h_pinned));

这里的同步保证释放前传输完成。真正流水线应把等待放在需要读取或复用 buffer 的位置，避免每个 chunk 入队后立即阻塞。

消费者只等待所需的数据

a_done 必须记录在生产者之后，消费者必须提交在 wait 之后。即使删掉 wait 后偶尔验证通过，也无法证明不存在跨流数据竞争。

注意事项

  • Pageable buffer 配上 musaMemcpyAsync，仍可能发生内部中转或 host 阻塞。API 名字不能证明拷贝与 kernel 真正重叠。
  • 没有同步的 CPU 计时容易只测到提交；event 计时必须确认目标 stream、计时边界和 stop 完成。多流总时间要覆盖全部相关工作。
  • 在每个 chunk 后插入 musaDeviceSynchronize() 会等待更大范围的工作，破坏原本可重叠的流水线；局部依赖优先用 event 表达。
  • 不同 stream 的 callback 不共享提交顺序。按编号消费结果时，应传递编号并由 host 排序，或为真正的执行依赖加入 event。
  • Graph 不会自动更快。记录 capture/instantiate 与 replay 的测量边界，保持 direct 与 graph 的 workload 一致，再实测比较。
  • 统一内存与 prefetch 的支持和表现随平台、SDK 改变；不能把 API 可调用或一次正确输出当作性能收益已验证。

精选题目

先说出判断依据，再展开核对。以下题目与完整题库保持一致。

Pinned memory 相比普通 pageable host memory，主要优化哪段？

Pinned host memory 更利于 DMA，通常能提升 H2D/D2H 拷贝带宽。

它不是让 kernel 算得更快，而是优化主机和设备之间的数据搬运。

跨 stream 建立依赖时，更适合用什么机制？

event 可以在一个 stream 记录完成点，在另一个 stream 等待它。

用 host sleep 猜时间不可靠，也会破坏调度。

跨多个 stream 的 callback 完成顺序能否当作提交顺序？

不能。不同 stream 之间没有天然的完成顺序，callback 触发顺序可能和 chunk 提交顺序不同。

需要按编号处理时，应把 chunk_id 投递给主线程或显式建立 event 依赖。

为什么不能因为 CUDA Graph 理论上能减少 launch overhead，就直接断言 MUSA Graph 一定更快？

Graph 的收益取决于 SDK、驱动实现、图中操作数量和 kernel 粒度，必须在相同 workload 和计时口径下实测。

API 能调用不等于优化收益已验证；小图的固定 graph 开销可能超过 direct launch。
