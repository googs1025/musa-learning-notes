  • 为什么 unrolling 不能修复地址模式，AoS 与 SoA 又怎样改变相邻线程的地址序列？
  • 转置为何必须分别检查 global read 和 write，shared tile 与 padding 分别解决什么问题？

核心知识

1. 时间要换算成有效带宽

Effective bandwidth 用约定的逻辑读写字节数除以 kernel 时间。SAXPY 的每个元素逻辑上读 x、读旧 y、写新 y，示例按 3 × N × sizeof(float) / time 估算。它是跨实验的统一指标，不等同于实际 DRAM 流量，也不能脱离数据规模、设备、SDK、预热与计时边界宣称硬件峰值。

2. Coalescing 看一组线程的地址

判断合并访存要观察同一条 load/store 上相邻线程的地址集合。访问 a[i]、a[i+1]、a[i+2] 通常更容易用较少的 global-memory 事务完成；只看单个线程的代码或数学工作量，无法说明吞吐。

3. Offset 改起点，不改 stride

in[i + offset] 中，相邻线程的元素步长仍为 1；统一 offset 改变的是访问区间相对 cache line 或内存事务边界的起点。不同 offset 可能覆盖不同数量的事务，但缓存和设备实现也会影响结果，因此要在相同口径下测多个 offset，不能把所有非零 offset 当成同一种代价。

4. Unrolling 不会重写地址关系

展开可以改变每线程工作量、循环和调度开销，但同一访问指令中各线程的基础地址仍保留原来的 offset、stride 与对齐关系。它可能有益、无益或因寄存器压力而变慢；是否改善只能结合地址序列、occupancy 与实测判断。

布局决定字段地址序列

AoS 把一个对象的 x/y/z/w 交错放在一起。当前 Particle 是四个 float，因此相邻线程读取 p[i].x 时地址相隔 16 字节；读取 p[i].y 也是另一条 16 字节步长的序列。只计算 x+y 时，z/w 不参与运算，却可能随内存事务或 cache line 一同搬运。

SoA 把字段拆成数组，相邻线程分别读取连续的 x[i] 和连续的 y[i]，每条字段访问的地址间隔为 4 字节，更容易合并。这个例子解释的是访问模式，而不是宣称 SoA 普遍更快：若算法总是消费对象的全部字段，AoS 的局部性、转换成本、缓存、对齐与具体设备都可能改变结论。

比较布局时先画出“同一条指令上线程 0、1、2……访问哪个地址”，再核对两版工作量、初始化、验证和计时次数是否一致。

转置要同时检查读和写

Naive：读连续，写跨步

输入为 row-major 的 H × W 矩阵时，线程以 in[y * w + x] 读取；固定 y、增加 x 会访问相邻元素。转置输出为 W × H，源码写 out[x * h + y]；对同一批沿 x 相邻的线程，写地址相隔 h 个元素。结果正确只证明索引完成了转置，不能证明写事务高效。

Shared tile：把方向变化放在片上

Tiled 版本先让线程按连续方向把输入写入 tile[ty][tx]，全 block 同步后交换 block 坐标和 tile 下标，再让全局输出写入沿线程 x 方向保持连续。shared memory 承担 tile 内的转置，__syncthreads() 建立装载阶段与读取阶段之间的可见性。

Padding：改变 shared-memory 行跨度

tile[TILE][TILE + 1] 的额外一列不改变矩阵逻辑，而是改变 shared-memory 相邻行的地址跨度。它可在目标 bank 映射下错开转置列访问，降低多个线程落到同一 bank 的概率。bank 数量、映射、同步成本、shared-memory 占用和边界处理均依赖实现，必须在目标设备上验证，不能因为用了 shared memory 或 padding 就保证加速。

Offset 保持连续步长，但移动访问起点

02 · Offset access（改编节选）
__global__ void offset_copy(const float* in, float* out,
                            int n, int offset) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        out[i] = in[i + offset];
    }
}

// 源码为输入多分配 64 个 float；测试的最大 offset 是 31。

边界条件保护实际输出下标 i；输入分配必须同时容纳 i + offset。源码用 N + 64 的输入分配覆盖其 offset 集合。

AoS 与 SoA 的字段 load

04 · 两种字段布局（改编节选）
struct Particle { float x, y, z, w; };

// AoS：线程 i 与 i+1 的同一字段相隔 sizeof(Particle)。
if (i < n) out[i] = p[i].x + p[i].y;

// SoA：每个字段数组中，线程 i 与 i+1 读取相邻 float。
if (i < n) out[i] = x[i] + y[i];

两段都计算 x+y；差别是字段在内存中的排列及一组线程产生的地址序列。

查看源码：04_aos_vs_soa.mu

Row-major 转置的输入与输出索引

05 · Naive transpose（改编节选）
int x = blockIdx.x * blockDim.x + threadIdx.x;
int y = blockIdx.y * blockDim.y + threadIdx.y;
if (x < w && y < h) {
    out[x * h + y] = in[y * w + x];
}

in[y*w+x] 按输入行连续读取；out[x*h+y] 使用输出行宽 h，对沿 x 相邻的线程形成跨步写。

查看源码：05_transpose_naive.mu

Padded tile 分隔装载与转置写回

06 · Shared padded transpose（改编节选）
__shared__ float tile[TILE][TILE + 1];

int x = blockIdx.x * TILE + threadIdx.x;
int y = blockIdx.y * TILE + threadIdx.y;
if (x < w && y < h) {
    tile[threadIdx.y][threadIdx.x] = in[y * w + x];
}
__syncthreads();

x = blockIdx.y * TILE + threadIdx.x;
y = blockIdx.x * TILE + threadIdx.y;
if (x < h && y < w) {
    out[y * h + x] = tile[threadIdx.x][threadIdx.y];
}

所有线程都到达同步点，第二阶段才读取 tile。当前示例的 2048×2048 尺寸可被 32×32 tile 整除；推广到非整 tile 边界时，还要避免有效输出读取未初始化的 tile 元素。

查看源码：06_transpose_padded.mu

注意事项

  • 只报告毫秒数不能说明带宽利用率；同时说明逻辑读写字节数、effective bandwidth、数据规模、计时范围、设备与 SDK。
  • 不要把所有 offset 一视同仁，也不要把 offset 误说成 stride；逐个测量起点相对事务边界的变化，并保持其他条件一致。
  • 不要声称 unrolling 会修复 coalescing；展开改变每线程工作量，却不一定恢复地址对齐或相邻线程的地址关系。
  • 转置不能只优化或描述读取一侧；分别列出 global read、global write 和 shared tile 的地址方向。
  • shared memory 并非自动无冲突或自动更快；检查 bank mapping、padding、同步、容量、occupancy 与边界 tile，并以实测收尾。

精选题目

先独立作答，再展开核对。以下问题、答案与易错点逐字取自完整题库。

Coalesced access 主要影响什么？

相邻线程访问连续地址时，硬件更容易合并内存事务，提高 global memory 吞吐。

数学计算少的 kernel 往往先被访存模式限制。

Shared memory transpose 为什么常用 padding？

padding 改变 shared memory 行跨度，降低多个线程访问同一 bank 的概率。

padding 多一个元素看似浪费一点空间，但常能换来更少 bank conflict。

AoS vs SoA 主要是在比较什么？

AoS/SoA 会改变线程读取字段时的地址分布，从而影响 coalescing。

面向 CPU 直觉舒服的数据布局，不一定适合 GPU。

为什么 unrolling 不能保证修复 offset 带来的访存损失？

展开可以减少循环或 launch 开销，但错误的访问布局仍可能限制带宽。

优化要拆分变量，分别观察访存模式、寄存器、occupancy 和端到端时间。
