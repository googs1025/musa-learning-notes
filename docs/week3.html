Week 3 · 线程协作

线程怎样协作完成一次归约？

从 warp 内分支开始，沿 shared memory、同步、unrolling 和 shuffle 逐步改写 reduce，再把线程坐标映射到二维 row-major 数据。

本周要回答的问题

  • 为什么同一个 warp/group 内线程走不同路径会降低有效并行度？
  • 一个 block 如何在 shared memory 中归约，block 之间的 partial sum 又由谁汇总？
  • 每线程加载两个元素和 warp shuffle 分别减少了哪些工作，又引入了哪些边界条件？
  • 二维 grid/block 的 (x, y) 如何对应 row-major 矩阵中的线性位置？

核心知识

1. Divergence 看的是同组路径

分支数量本身不是代价。若同一 warp/group 内各 lane 对条件的判断不同，硬件需要分段执行路径并暂时屏蔽不匹配的 lane，有效并行度会下降；若整组线程选择一致，即使存在 if，也不会因这个条件产生分支分化。

2. 对照实验也要看工作量

01_warp_divergence.mu 的 coherent 条件按 blockIdx.x 分组，divergent 条件按 threadIdx.x 奇偶交替。但两条 divergent 路径分别使用乘法和除法，因此测得的 slowdown 同时包含控制流与算术差异，不能当作纯 divergence 成本。

3. Warp 参数必须面向目标确认

CUDA 示例常把 32-thread warp 和相应 mask 写进代码；这些不是跨平台常量。MUSA 的实际 warp/group 宽度、mask 语义和兼容 intrinsic 行为应以目标设备、当前 SDK 与实测为准。仓库示例的注释和常数是阅读起点，不是对所有 MUSA 目标的保证。

从 block 归约到 shuffle

Shared-memory tree reduction

naive 版本先让每个线程把一个输入元素搬进 shared memory，越界位置填 0；随后每轮把后半段加到前半段，并在轮次之间调用 __syncthreads()。这个 barrier 只覆盖同一个 block，所以每个 block 最终只能安全地产生一个 partial sum。当前折半循环还要求 block size 是 2 的幂；任意 N 能通过尾段补 0 处理，不代表任意 block size 都适用于这棵归约树。

跨 block 的最终汇总必须进入新阶段：教学示例把 partial 数组拷回 host 后串行相加，也可以再启动第二个 reduction kernel。不能用一次 block barrier 假装同步整个 grid。

Unroll2：每线程先合并两个元素

unrolling 示例让一个 block 覆盖 2 * blockDim.x 个输入元素。每个线程先在寄存器中合并 in[i] 与 in[i + blockDim.x]，再进入相同的 shared-memory tree；这样通常减少 block 数和部分调度、循环与 global-memory 中间工作，但性能仍需在相同计时口径下实测。

尾段不能只检查第一个位置：两次加载都要独立判断边界。对任意 N，越界元素应贡献 0 或不参与访问。

Shuffle：寄存器交换有明确范围

shuffle 让同一个 warp/group 内的 lane 直接交换寄存器值，可省去这一级 shared memory 与 block-wide barrier。它不能跨 warp 或跨 block；仓库实现仍把各 warp 的和写入 shared memory，执行一次 __syncthreads()，再由第一个 warp 完成第二级归约。

当前仓库的 nested hello 示例也要按源码理解：它由 host 启动 parent、等待完成，再启动 child，是 host 编排的两阶段 kernel 调度，并非 kernel 内再次 launch kernel 的 device-side dynamic parallelism。

二维线程与 row-major 映射

二维 block/grid 只是线程组织方式。线程用 x 维定位列、y 维定位行：x = blockIdx.x * blockDim.x + threadIdx.x，y = blockIdx.y * blockDim.y + threadIdx.y。row-major 矩阵中，元素地址是 y * width + x。

仓库的矩阵示例让每个有效线程读取一个 m[y * width + x]，并用 atomicAdd(&rows[y], ...) 累加对应行。多个 x 坐标会竞争更新同一行，atomic 保证更新正确但可能形成竞争；二维 launch 不意味着数据只能是二维，一维线程布局同样可以通过除法和取模恢复坐标。

用条件位置构造 coherent / divergent 对照

01 · 分支条件对照（改编节选）
if (mode == 0) {
    if (blockIdx.x & 1) x = x * 1.0001f + 1.0f;
    else x = x * 1.0001f + 1.0f;
} else {
    if (threadIdx.x & 1) x = x * 1.0001f + 1.0f;
    else x = x / 1.0001f - 1.0f;
}

前者在一个 block 内条件一致；后者让相邻线程交替选择路径。两条 divergent 路径的算术不同，所以这里只能作为综合对照。

每轮同步的 shared-memory tree

02 · Block 内归约（原码节选）
s[tid] = (i < n) ? in[i] : 0.0f;
__syncthreads();
for (int stride = blockDim.x / 2; stride > 0; stride >>= 1) {
    if (tid < stride) s[tid] += s[tid + stride];
    __syncthreads();
}
if (tid == 0) partial[blockIdx.x] = s[0];

第一次同步保护 shared load；循环中的同步保证下一轮读取上一轮已经写完的值。这里只得到 block partial。

查看源码：02_reduce_naive.mu

先做组内 shuffle，再合并各组结果

04 · Shuffle 归约（改编的结构伪代码）
warp_reduce_sum(v, mask) {
    // mask 的类型和值必须由目标 MUSA SDK 与设备确认。
    for (int offset = warpSize / 2; offset > 0; offset >>= 1) {
        v += __shfl_down_sync(mask, v, offset);
    }
    return v;
}

v = warp_reduce_sum(v, mask);
int lane = tid % warpSize;
int warp = tid / warpSize;
if (lane == 0) warp_sums[warp] = v;
__syncthreads();
// warp_sums 的第二阶段归约另行处理，此处省略。

这段结构伪代码只保留源文件的数据流；mask 是无类型、无取值的形参占位，必须从目标 MUSA SDK 与设备能力中确认。调用名沿用源码符号，也不代表跨目标可直接使用。链接中的当前源码仍含 CUDA 派生的硬编码 mask，使用前必须审计其 mask、函数签名和 group 宽度，不能从 CUDA 32-lane 习惯反推。

从二维线程坐标得到 row-major 地址

06 · 二维行求和（原码节选）
int x = blockIdx.x * blockDim.x + threadIdx.x;
int y = blockIdx.y * blockDim.y + threadIdx.y;
if (x < width && y < height) {
    atomicAdd(&rows[y], m[y * width + x]);
}

x 对应列，y 对应行；两个维度都要做边界判断。线性位置 y * width + x 来自 row-major 布局，而不是 launch 语法。

注意事项

  • 不要硬编码 CUDA 的 32-thread warp、mask 或 reduction 深度并把它们当成 MUSA 通用结论；查询目标设备和 SDK 的实际语义。
  • shared-memory reduction 的 load 后及相邻轮次之间不能漏掉所需同步，否则线程可能读取尚未写完的数据。
  • 输入长度不整除 block size 或 unroll 粒度时，每个加载位置都要保护；尤其不能只检查 unroll 后的第一个地址。
  • shuffle 只在 warp/group 范围交换寄存器值，不能替代跨 warp 的 block-wide 协作，更不能同步不同 block。
  • launch 使用一维还是二维只描述线程组织，不决定数据本身的维数；索引公式才决定线程访问哪个元素。
  • 当前 05_nested_hello.mu 是 host 同步后的两阶段启动，不应描述成已经实现了 device-side dynamic parallelism。

精选题目

先独立作答，再展开核对。问题、答案与易错点和完整题库保持一致。

Warp divergence 的核心问题是什么？

SIMT 执行中，同一 warp 内分支不一致会让路径被分段执行，降低有效并行度。

不是所有 if 都严重，关键看同一 warp 内是否分歧。

MUSA 做 warp-level shuffle/reduce 时，为什么不能照搬 CUDA 的 warp=32 假设？

MUSA warp size 通常按 128 理解，shuffle mask、warp 数量、reduction tree 深度都要重新算。

这里的 128 只对应题目采用的示例语境；实际目标的 warp/group 宽度必须向目标设备查询，并结合所用 MUSA SDK 确认。

代码语法接近 CUDA，不代表调优参数可以机械照搬。

为什么 naive reduce 需要 host final reduce 或第二个 kernel？

每个 block 只能安全地产生自己的 partial sum，跨 block 汇总需要新的阶段或专门的全局同步机制。

把 block barrier 当成 grid barrier 是 reduce 中最常见的概念错误。

reduce 的输入长度不是 block size 或 unroll 粒度整数倍时，尾部元素如何处理？

每次加载都做边界判断，越界线程使用 0 或直接退出，不能越界读写。

对本页的 shared-memory reduction，越界线程必须写入 0，并继续参加后续所需的 barrier；只有后续协作和同步不再依赖该线程时，才可以提前返回。

只检查第一个加载位置而忘记检查 unroll 后的第二个或更多位置。
