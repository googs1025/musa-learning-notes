核心知识

错误触发与错误报告可能分离

异步 kernel 的 launch 返回后，设备仍可能正在执行。后续 API 报告错误时，应回溯此前提交的工作，结合源码、线程索引和同步边界定位原因。

每条链路都要有可检查的结果

多卡通信要核对每个 rank 的输出；框架调用要确认输入输出的 device、dtype、shape 与数值；故障记录要让其他人能重现同一条件。编译、import 或设备发现只覆盖各自的一步。

本周源码包含环境相关的骨架与故意失败的调试样例。MCCL 示例尚未执行 AllReduce，custom op 示例尚未实现自定义 MUSA kernel；真实运行结果需在配套 SDK 和硬件上验证。

调试：从同步点回到触发指令

musaGetLastError() 用于检查 launch 后的错误状态，不能证明异步 kernel 已正确完成；musaDeviceSynchronize() 等待设备工作完成，也可能报告此前执行中的错误。本周样例只分配 1024 个 float，却让 2048 个线程无边界检查地写入，预期在同步时观察到 illegal address。若未触发，也应如实记录，不能把越界行为当作正确。

源码级调试需要带调试符号，并使用本机 SDK 支持的优化设置与调试器功能。应结合断点、线程索引、地址和源码行找到失败指令，检查指针与分配范围。默认构建不能自动视为适合调试；具体构建参数和设备端调试能力以对应 SDK 为准。

Error dump 要能对应一次明确的复现

按本机 SDK 文档启用 Error Dump，保留原始 dump/log 与完整标准输出、错误输出，同时记录源码版本、SDK/驱动版本、设备型号与卡数、编译命令、输入规模、运行命令、相关环境变量和复现步骤。用时间戳及文件清单确认文件属于本次运行；未复现错误或未生成 dump 也要写明。具体开关、字段和输出路径随环境核对。

多卡：身份、设备与 collective 顺序

rank 是通信域中当前参与者的逻辑编号，nranks 是参与总数，device 是本进程选择的本地 GPU。多机运行时 global rank 不能直接当本地设备号，必须核对 launcher 提供的映射。communicator 则是所有 rank 共同加入的通信上下文；各 rank 的 device、stream 和 buffer 需要对应。

AllReduce 把各 rank 的输入按约定运算归约，并让每个参与者获得归约结果。完整调用流程需要向所有 rank 分发同一个 unique id，选择本地 device、创建 stream 与 buffer，初始化 communicator，再按一致顺序进入 mcclAllReduce。各 rank 的元素数量、类型和归约操作也要匹配，最后同步并核对各自输出。当前骨架仅展示设备与 stream 准备，以及待补齐调用的提示。

P2P 是否可用取决于设备能力、互联拓扑和运行环境。两张卡可见并不证明它们能直接互访；先探测并记录支持情况，再讨论 peer access、通信路径和带宽。仓库 CUDA P2P 对照样例的能力不能直接推定为当前 MUSA 环境的能力。

框架：沿真实算子链路检查

torch_musa 最小 smoke test 依次加载后端、发现设备、创建 MUSA tensor、执行算子、同步并回 CPU 取样。它将 Python API、后端实现、runtime 和设备执行连接起来。设备可用或 import 成功还不足以覆盖实际算子；一个 ReLU 样例通过也只说明这组输入与算子的链路可用。

Custom op 的四层边界

Schema 定义算子名称、参数与返回值契约；注册让框架找到入口；dispatch 根据设备等条件选择实现；kernel 才负责设备计算。检查时要把这些层与 tensor 的 dtype、shape、device、布局、当前 stream 和返回值一起核对。

本周 C++ 文件用 PYBIND11_MODULE 和 m.def 暴露 Python 扩展函数；这不是 PyTorch Dispatcher 的 schema 或 MUSA dispatch 注册。函数只检查 contiguous 后调用 x.clone()，没有显式 MUSA 设备检查，也没有自定义 kernel。要扩展成完整 MUSA 算子，需补齐设备契约、对应注册与实现，并验证 Python 调用、设备执行和错误传播。

故意越界，在同步点观察

02 / 03 · Illegal address（改编节选，故意失败）
__global__ void write_oob(float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    out[i] = float(i);  // 故意缺少 if (i < n)
}

// 只分配 1024 个 float，却启动 8 × 256 个线程。
float* d_out = nullptr;
MUSA_CHECK(musaMalloc(&d_out, 1024 * sizeof(float)));
write_oob<<<8, 256>>>(d_out, 1024);
MUSA_CHECK(musaGetLastError());
MUSA_CHECK(musaDeviceSynchronize());

同步点报告的是此前越界写可能造成的错误。02 用于调试器定位，03 用于采集 Error Dump；两者共享故障模型，诊断证据的产物不同。

Tensor 创建、运算、同步与 CPU 取样

04 · torch_musa smoke test（节选）
import torch
import torch_musa

if torch.musa.is_available():
    x = torch.randn(1024, device="musa")
    y = x.relu()
    torch.musa.synchronize()
    print("sample", float(y[0].cpu()))

回 CPU 打印一个标量验证结果链路可观察；源码没有完整数值断言。进一步验证应使用确定性输入与 CPU 参考值比较，并覆盖所需 dtype、shape；这段取样代码不能用来报告性能。

Python 绑定与实际 MUSA 实现的边界

05 · Custom op 绑定骨架（节选）
torch::Tensor identity_musa(torch::Tensor x) {
    TORCH_CHECK(x.is_contiguous(), "expected contiguous tensor");
    return x.clone();
}

PYBIND11_MODULE(TORCH_EXTENSION_NAME, m) {
    m.def("identity_musa", &identity_musa, "identity custom op skeleton");
}

m.def 把 C++ 函数暴露到 Python 扩展模块，x.clone() 使用已有张量操作。函数名带有 musa 不代表已注册 MUSA dispatch；需要验证输入输出设备、布局限制与数值，再评估真正 kernel 实现的边界。

查看源码：05_torch_musa_custom_op.cpp

注意事项

  • 后续 API 报错时要回溯先前异步工作，不能把报告错误的同步调用直接认作触发位置。
  • 保存 dump 时同时保存环境、命令、输入与复现步骤，避免只留下最后一行错误或误用旧 dump。
  • 区分 global rank、local rank 与 device id，核对每个参与者的 communicator、stream 和 buffer 配套关系。
  • 使用 P2P 前先检查设备能力与拓扑，不要仅凭卡数推断互访支持或通信带宽。
  • Custom op 验证应覆盖注册、dispatch 和 Python 调用边界；kernel 正确不能替代 dtype、shape、device、布局及返回值检查。

精选题目

先独立作答，再展开核对。以下问题、答案与易错点逐字取自完整题库。

为什么调试 illegal address 时，错误经常不是在 kernel launch 这一行立刻报出？

kernel 执行是异步的，运行期错误通常要到后续同步点才暴露。

这就是 launch 后同时检查 musaGetLastError() 和 musaDeviceSynchronize() 的原因。

torch_musa 最小 smoke test 至少应该验证哪条链路？

需要验证设备发现、MUSA tensor、实际算子、同步边界和回 CPU 结果。

is_available() 为真只能说明设备或后端可见，不能代表完整算子链路已通过。

MCCL AllReduce 示例中的 rank、nranks 和 device 分别描述什么？

rank 标识当前参与者，nranks 是 collective 的参与总数，device 是本地 GPU 选择。

多卡 collective 要求所有 rank 以一致顺序进入同一个通信操作。

一个可复现的 MUSA error dump 记录至少应包含哪些环境信息？

应记录 SDK/驱动版本、设备型号、编译命令、输入规模、运行命令、错误信息和复现步骤。

只保存最后一行错误而不保存环境，通常无法判断是代码、版本还是硬件差异。

torch_musa custom op 的边界检查为什么不能只看 kernel 本身？

custom op 是框架、C++ 扩展和 MUSA kernel 的边界，类型、设备、注册和返回值都必须正确。

底层 kernel 正确不代表框架调用路径和不同输入条件都正确。
