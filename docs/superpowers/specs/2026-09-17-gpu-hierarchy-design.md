# GPU 结构层次文档设计

日期：2026-09-17

## 目标

为已有 MUSA 学习材料新增一篇独立的 GPU 结构层次教程。教程先用生活比喻帮助初学者建立直觉，再把 kernel、grid、block、warp、thread 映射到硬件执行路径，使读者能够把层级知识用于 kernel 配置和初步性能分析。

本文档只覆盖公开资料能够确认的 MUSA `MPC → MPX → MP` 层级。`MPE` 不纳入本次内容，因为当前采用的摩尔线程公开编程指南没有把它列为该硬件层级中的正式术语。

## 读者与深度

目标读者是已经开始阅读本仓库 Week 1 材料、但尚未建立 GPU 硬件心智模型的学习者。

内容采用“入门心智模型 + 工程实践”的深度：

- 先解释各层是什么，用一套贯穿全文的物流园比喻降低理解门槛。
- 再解释软件任务如何映射到硬件，以及这种映射为何会影响 block 大小、warp 利用率、资源驻留和延迟隐藏。
- 不展开芯片微架构逆向、具体时序或未公开的内部调度实现。

## 主文档结构

`docs/gpu-hierarchy.md` 使用以下章节：

1. 一张总图：展示 `GPU → 工作分发 → MPC → MPX → MP → warp/执行单元`。
2. 物流园比喻：用订单、园区分区、车间组、车间、班组和工人解释层级。
3. MUSA 硬件层级：分别解释 MPC、MPX、MP 及它们共享的缓存或计算资源。
4. CUDA 近似对照：说明 GPC、SM、SM sub-partition、warp scheduler 等概念可怎样辅助理解，以及为何不能视为严格等价。
5. 软件到硬件：解释 kernel、grid、block、warp、thread 的调度和执行边界。
6. 一个 kernel 的旅行：沿一次 launch 的路径串起所有概念。
7. 对性能的影响：block 大小、warp 利用率、驻留资源、occupancy 和延迟隐藏。
8. 常见误区：纠正软件层级等同于物理层级、名称一一映射、高 occupancy 必然更快等误解。
9. 参考资料：列出摩尔线程和 NVIDIA 官方资料。

## 核心图与比喻

主图采用文本图，确保 GitHub、终端和静态文档环境都能直接阅读：

```text
GPU
├── 前端 / 工作分发（使用通用描述，不绑定未确认专名）
└── MPC × N
    ├── MPX × N
    │   ├── MP × N
    │   │   ├── warp 调度与执行
    │   │   ├── FP / INT / SFU / TCE 等计算单元
    │   │   └── 局部存储与缓存
    │   └── 共享缓存
    └── 共享缓存
```

比喻映射如下：

| 概念 | 比喻 | 表达边界 |
|---|---|---|
| kernel | 一整批订单 | 表示要在 GPU 上执行的工作程序 |
| grid | 订单总清单 | 表示一次 launch 产生的全部 block |
| block | 不可拆散的一箱任务 | 整个 block 在同一 MP 上驻留和执行 |
| MPC | 物流园分区 | 表示多个下级计算组织的较高层分组 |
| MPX | 一组相邻车间 | 表示多个 MP 的执行引擎分组 |
| MP | 真正接活的车间 | block 驻留、warp 被管理和执行的主要处理器 |
| warp | 同一节拍工作的班组 | 表示 SIMT 执行分组 |
| thread | 班组里的工人 | 各线程拥有自己的索引和数据 |

比喻只负责建立直觉。正文随后立即给出技术定义，防止读者把物流组织细节错误套到硬件实现上。

## MUSA 与 CUDA 的对照原则

文档区分编程模型对应和物理架构类比：

- `thread / warp / block / grid` 在两套编程模型中可直接对照，但 warp 宽度等设备属性必须以目标平台为准。
- MUSA MP 可用 CUDA SM 帮助理解，因为两者都是 block 驻留并执行 SIMT 工作的主要处理器层级；正文仍称其为近似对应。
- MUSA MPC 可用 CUDA GPC 的“多个处理器组成较高层分组”帮助理解，但不推断两者拥有相同的资源边界和调度职责。
- MUSA MPX 可参考 NVIDIA SM sub-partition 的“处理器内部执行资源分组”思想，但不写成严格对应，因为公开资料中的层级位置和资源归属并不相同。
- 前端调度只使用“接收、排队和分发工作”的通用说明，不为 MUSA 前端绑定未经当前公开资料确认的专名。

所有对照表均使用“近似理解”“不能画等号”等明确措辞。

## 执行路径

教程沿下面的路径描述一次 kernel：

```text
CPU 提交 kernel
  → GPU 前端接收工作
  → grid 中的 block 等待分配
  → 可用 MP 接收完整 block
  → block 被划分为 warp
  → 调度逻辑选择就绪 warp
  → FP、INT、访存等执行管线完成指令
```

其中只陈述编程模型保证的行为。具体 block 分发策略、指令发射宽度和内部流水实现标记为架构相关，不进行无来源推断。

## 工程结论

正文以三个问题连接到实际编程：

1. block 的线程数为何通常选择 warp 大小的整数倍：减少尾部 warp 中长期空闲的 lane。
2. 寄存器或片上存储使用为何影响并发驻留：单个 block 消耗越多有限资源，同一 MP 可同时容纳的 block 或 warp 越少。
3. occupancy 为何不是越高越好：更高驻留度通常更有利于隐藏等待，但最终性能还受指令吞吐、访存、数据复用和依赖链影响。

示例避免写死未经设备查询确认的 MUSA warp 宽度、缓存大小或单元数量。涉及 MP_10、MP_21 的数量时，只作为带来源的具体架构例子，不推广到所有 MUSA GPU。

## 事实标注与来源

正文按三类措辞表达事实：

- 官方明确说明：可直接陈述，并链接对应官方章节。
- 近似类比：使用“可类比”“帮助理解”等限定语。
- 架构相关：提醒读者查询具体设备、计算能力和 SDK 文档。

主要资料：

- 摩尔线程《MUSA 编程指南》的“硬件架构”章节，用于 MPC、MPX、MP、缓存层级和 MP_10/MP_21 示例。
- 摩尔线程《MUSA 编程指南》的“GPU 并行计算”章节，用于 block 到处理器的调度模型。
- NVIDIA CUDA Programming Guide 的 Programming Model，用于 GPC、SM、warp 和 block 的 CUDA 侧定义。
- NVIDIA Nsight Compute Profiling Guide 的 Streaming Multiprocessor 章节，用于 SM sub-partition 和 warp scheduler 的 CUDA 侧说明。
